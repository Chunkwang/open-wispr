# Sign-in design (Days 4–5)

Decided by the tech-lead review on 2026-09-25. Everything here runs against local mocks until Day 16 (real Supabase). Items marked **VERIFY-ON-DAY-16** rely on memory of Supabase behaviour and must be checked against the real project.

## 1. Decision: 6-digit email code, not a magic link (D2 amended, Task 3.1 deferred)

- The dev app is a bare binary (`.build/debug/open-wispr`), so a URL-scheme callback (`CFBundleURLTypes`) cannot reach it; even the bundled app needs LaunchServices registration. Codes need none of that.
- Corporate link scanners (Outlook Safe Links and similar) pre-click magic links and burn the one-time token. Codes are immune.
- Sign in with Apple later needs no URL scheme (native `ASAuthorizationController`, then `POST /auth/v1/token?grant_type=id_token`).
- Costs accepted: users type a code; the email template must contain `{{ .Token }}` (Day 16); a relayed code can be phished (as can a link); brute force is limited by Supabase's per-IP verify limits, a short expiry and single use (set OTP expiry to 600 s on Day 16; default is 3600). **VERIFY-ON-DAY-16.**
- Task 3.1 (URL scheme) is deferred until a link or OAuth-redirect flow is wanted. Sign in/out menu items are DEBUG-only until Day 16, like the Rewrite menu.

## 2. Mock API (`backend/proxy/scripts/mock-supabase.mjs`, node:http, no new dependencies, 127.0.0.1:54321)

Mirrors GoTrue endpoints and JSON shapes. Errors: `{"code":<http>,"error_code":"<x>","msg":"<text>"}`. The client classifies by HTTP status and `error_code` and also tolerates `error`, `error_description`, `message`; it never matches message text. Missing `apikey` header: 401 `{"message":"No API key found in request"}` (as today).

- `POST /auth/v1/otp` body `{"email","create_user":true}`: 200 `{}`. Invalid email: 400 `validation_failed`. A second send within `MOCK_OTP_RESEND_SECONDS` (default 60): 429 `over_email_send_rate_limit` with a `Retry-After` header (whether real Supabase sends it: VERIFY-ON-DAY-16; the client falls back to 60 s). A new code replaces the old. Codes are 6 digits from `crypto.randomInt` (or `MOCK_FIXED_CODE`). Prints `mock-supabase: code for <email> is <code>` to stdout: the only place a secret is printed, and only in the mock.
- `POST /auth/v1/verify` body `{"type":"email","email","token"}`: 200 session; wrong, expired or used code: 403 `otp_expired` (real GoTrue does not distinguish wrong from expired, so the mock must not either); `MOCK_MAX_VERIFY_ATTEMPTS` (default 5) wrong tries for one email: 429 `over_request_rate_limit` for 60 s; non-numeric token or `type` other than `email`: 400/422 `validation_failed`. Code lifetime `MOCK_OTP_TTL_SECONDS` (default 600).
- Session JSON: `{"access_token","token_type":"bearer","expires_in","expires_at","refresh_token","user":{"id","aud":"authenticated","role":"authenticated","email"}}`. Refresh tokens are opaque 12-char base64url. Access token: HS256 JWT with `aud=authenticated`, `iss=${SUPABASE_URL}/auth/v1`, UUID `sub` (UUID v5 of the lowercased email), `iat`, `exp`, `email`, `role`, `session_id`, `app_metadata`, `user_metadata`; TTL `MOCK_ACCESS_TTL_SECONDS` (default 3600; 60 for Day 5); signed with `SUPABASE_JWT_SECRET` (env, else `.dev.vars`; exit if it does not start with `local-dev-`). Share the `.dev.vars` reader with `mint-dev-token.mjs` in one helper.
- `POST /auth/v1/token?grant_type=refresh_token` body `{"refresh_token"}`: 200 session with rotation; unknown token: 400 `refresh_token_not_found`; rotated-out token: 400 `refresh_token_already_used` and the whole session's tokens die (reuse detection). Real GoTrue has a ~10 s reuse window, so the client must serialise refreshes (single-flight).
- `POST /auth/v1/logout?scope=local` with `Authorization: Bearer <access>`: 204 and that session's refresh tokens are revoked; bad JWT: 401 `bad_jwt`. The client ignores the result.
- Dev-only routes (answer only to a loopback `Host`, else 404): `GET /__dev/last-code?email=` -> `{"code":"123456"}` or 404; `POST /__dev/fail {"route":"otp|verify|token|logout|any","mode":"503|429|500|drop|hang","times":n}`; `POST /__dev/revoke {"email"}` (kills refresh tokens; access tokens live until `exp`); `POST /__dev/reset`. The existing `MOCK_FAIL` env stays.
- Tests: `node --test scripts/mock-supabase.test.mjs` (built-in runner, port 0, no deps), added to the CI `backend` job; includes a `jose` `jwtVerify` of the issued token with the same options as `auth.ts`.

## 3. Client design (Swift)

Files in `Sources/OpenWisprLib/`:
- `AuthSession`: Codable, Equatable, Sendable `{accessToken, refreshToken, expiresAt: Date, email}` (epoch seconds), `needsRefresh(now:leeway: 60)`; `description`/`debugDescription` are redacted so interpolation cannot leak tokens.
- `SessionStore`: `load() -> Result<AuthSession?, KeychainError>`, `save(_:) throws`, `clear()`, `isSignedIn`. ONE Keychain item, account `"session"`, service unchanged.
- `AuthService`: `requestCode(email:)`, `verifyCode(email:code:)`, `signOut(_:)` on Day 4; `refresh(_:)` on Day 5. Async, returns `Result<_, AuthError>`, never throws, injectable `URLSession` and clock; uses `RewritePipeline.makeSession(.ephemeral, timeout: 10)`.
- `AuthError`: `invalidEmail`, `codeRejected`, `tooManyAttempts(retryAfter)`, `sendRateLimited(retryAfter)`, `offline`, `timedOut`, `unreachable`, `unavailable`, `invalidResponse`, `sessionRevoked` (Day 5), `storageFailed`.
- `AuthConfig`: URL and public anon key resolution. Auth calls go straight to Supabase, not through our proxy. The client holds only the project URL and the PUBLIC anon/publishable key (`apikey` header), never the service-role key, an `sb_secret_*` key or the JWT secret; a test asserts the shipped key is not a JWT with `role=service_role` and does not start with `sb_secret_`. Release defaults: URL `https://auth.invalid` and a placeholder key until Day 16. DEBUG-only overrides `OPENWISPR_AUTH_URL` and `OPENWISPR_AUTH_ANON_KEY` with the same rules as the proxy URL (https, or http to loopback only, else the default); generalise `RewritePipeline.resolveBaseURL` to take a `default:` parameter and keep its tests.
- `SignInWindow` plus a model with an injectable service (state machine unit-tested); `SignInCopy.swift` maps `AuthError` to text in one place, lint-tested like `RewriteNoticeTests`.
- `Keychain.swift`: add `write(_ data: Data, account:) throws` (`SecItemUpdate` first, `SecItemAdd` on `errSecItemNotFound`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` on both paths, OSStatus surfaced). `read` returns nil ONLY for `errSecItemNotFound`; any other status is an error and the session is NOT treated as signed out (a locked screen, `errSecInteractionNotAllowed`, must not delete anything). Undecodable JSON: delete the item and treat as signed out. Never log a value. The legacy DEBUG `session-token` item is deleted at launch (no migration). Remove the DEBUG "paste dev session token" items and the `authAccount` constant; dev tokens now come from the mock. Dev friction: SwiftPM ad-hoc re-signing can trigger a Keychain access prompt after each rebuild.

Day 4: `requestCode`, `verifyCode`, store the session, sign-out (clear Keychain first, then a best-effort `logout` capped at 3 s), the window, DEBUG-only menu items ("Sign in…", or a disabled "Signed in as <email>" plus "Sign out"). `RewritePipeline.keychainToken()` and the gate's `hasToken` read `SessionStore` (access token as-is, no refresh) so the demo flips "Rewrite: needs sign-in" to on. Signing in or out calls `RewriteCoordinator.resetSession()`.

Day 5: `SessionManager` actor: `validAccessToken()` refreshes when `expiresAt` is under 60 s away, single-flight, saves the rotated pair atomically; it is the pipeline's async `tokenProvider`; `RewriteGate.hasToken` becomes `SessionStore.isSignedIn`. Refresh outcomes: 400 with `refresh_token_not_found`, `refresh_token_already_used`, `session_not_found` or `session_expired` -> sign out and show the notice; offline, timeout, 429, 5xx or malformed -> keep the session, use the old token or insert raw, retry next time (never sign out on a transient error). On a proxy 401: force one refresh and retry once, then sign out (Task 3.7). The DictationSequencer watchdog is 8 s: refresh is capped at 2 s and counts inside the pipeline's 6 s total deadline.

New outbound connection: the email address and code go to Supabase and its SMTP provider. Add to the `TRUST.md` inventory (Task 5.3) and the privacy policy.

## 4. Task 2.3: `auth.ts` accepts HS256 secret OR JWKS

- Config: `JWT_VERIFY_MODE` in `[vars]` (`hs256` default | `jwks`), optional `SUPABASE_JWKS_URL` (default `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`; off loopback it must be https on the same origin as `SUPABASE_URL`). The mode comes only from config, never from the token header; `jku`/`x5u`/`jwk` headers are ignored. Any other mode value: 500 `misconfigured` (fixed body, fail closed).
- Allow-lists: hs256 mode accepts only `["HS256"]`; jwks mode only `["ES256","RS256"]`; `none` never.
- `hostGuard.ts`: the secret checks apply only in hs256 mode; `SUPABASE_JWT_SECRET` is not required in jwks mode.
- JWKS fetch: jose `createRemoteJWKSet`, module-level cache keyed by URL, `timeoutDuration` 3000, `cacheMaxAge` 600000, `cooldownDuration` 30000. All existing checks (`iss`, `aud`, `exp`, UUID `sub`) still apply.
- Failure mapping: JWKS fetch failure, timeout or malformed JWKS throws `AuthUnavailableError` and `index.ts` answers 503 `service_unavailable` (same fixed body and log kind as a tier outage; the user's token was not shown to be bad, and a 401 would push the client into refresh and sign-out). An unknown `kid` or a bad signature stays 401 (attacker-controlled input must never cause a 503).
- Tests (vitest; `jose` `generateKeyPair` for ES256/RS256, JWKS served through the `test/helpers.ts` fetch mock): hs256 valid; wrong secret; ES256/RS256 tokens rejected in hs256 mode; HS384; `alg:none`; jwks valid ES256 and RS256; bad signature; unknown `kid` -> 401; HS256 token signed with the public key bytes (algorithm confusion) -> 401; a `jku` header triggers no fetch; caching (two requests, one JWKS fetch) and rotation after the cooldown; 503 for JWKS 500, network throw, hang past 3 s, malformed JSON; `iss`/`aud`/`exp` still enforced; invalid mode -> 500; jwks mode needs no secret; the existing hs256 tests pass unchanged. Stretch: `MOCK_JWT_MODE=es256` in the mock for a local end-to-end run.

## 5. Task 2.2: `backend/supabase/migrations/0001_profiles.sql`

- Table `public.profiles(id uuid primary key references auth.users(id) on delete cascade, tier text not null default 'free' check (tier in ('free','pro')), stripe_customer_id text unique, created_at timestamptz not null default now())`. No email column (it lives in `auth.users`).
- `handle_new_user()` is `security definer` with `set search_path = ''`, every reference fully qualified: `insert into public.profiles (id) values (new.id) on conflict do nothing`. Revoke execute from public, anon and authenticated. Trigger `after insert on auth.users for each row`, created idempotently; backfill existing users with `on conflict do nothing`.
- RLS enabled on `profiles`; the only policy is `select to authenticated using ((select auth.uid()) = id)`; no insert, update or delete policies.
- Grants: Supabase's default privileges grant ALL on new public tables to anon and authenticated, so an explicit revoke is REQUIRED and is the real protection: `revoke all on public.profiles from anon, authenticated; grant select (id, tier) on public.profiles to authenticated;` (hides `stripe_customer_id`). `service_role` keeps full access (BYPASSRLS); the Worker uses it. The migration must be re-runnable.
- Sanity check: commit `backend/supabase/scripts/check-migration.mjs` (no `package.json` change). It loads PGlite (WASM Postgres) from a scratch directory named by an env var and prints the install command if missing. Harness stubs `auth.users(id, email)`, `auth.uid()` reading `request.jwt.claims`, roles anon/authenticated/service_role (BYPASSRLS), and `alter default privileges ... grant all ... to anon, authenticated, service_role` to mimic Supabase. Assertions: inserting a user creates a `free` row; user A sees only their row; `update ... set tier='pro'` fails 42501; insert and delete fail 42501; selecting `stripe_customer_id` fails; anon reads nothing; `service_role` updates the tier; the migration runs twice. Not verified offline: that PGlite installs (needs network) or matches Supabase's real grants. The Day 16 run against the real project with a real user token stays mandatory.

## 6. Security rules for sign-in (all builders)

- Never log the code, email, tokens, request or response bodies. Log only fixed categories (e.g. `auth: verify failed (code_rejected, 403)`). Email and code go only in POST bodies, never in URLs. The mock's console line is the sole exception.
- Brute force: Supabase is the authority; the client counter is UX only. After 5 wrong entries disable Submit for 30 s and offer "Send a new code" (a new code invalidates the old one). The counter lives in memory and resets when the window closes.
- Code entry: accept 6 to 10 digits (OTP length is configurable, VERIFY-ON-DAY-16); strip spaces and dashes on paste; disable autofill and suggestions; enable Submit at 6 or more digits.
- Expiry: the client stamps the request time; after 600 s it shows the "expired" copy without calling the server.
- Pasteboard: after a successful verify, if the pasteboard string equals the entered code, `clearContents()`; otherwise leave it. Never touch it while a dictation insert is in flight.
- Email: trim; check only one `@`, no whitespace or control characters, at most 254 characters (the server is the authority). Held in memory during the flow and persisted only in the session Keychain item after success; never in UserDefaults or `config.json`. Copy must not reveal whether an account exists.
- Rate-limit UX: Resend is disabled with a visible countdown from `Retry-After` (default 60 s).
- Copy keys the designer writes (`SignInCopy`), brand voice (calm, no exclamation marks, no "Oops", no apology, none of smart/seamless/powerful/magic/simply): `emailPrompt`, `sendingCode`, `codeSentTo(email)`, `codePrompt`, `signedIn`, `signedOut`, `signOutSignedOutNotice`, `invalidEmail`, `codeRejected` (one string for wrong OR expired, since the server cannot tell), `codeExpiredLocal`, `tooManyAttempts(waitSeconds)`, `resendCooldown(waitSeconds)`, `offline`, `timedOut`, `serviceDown` (5xx, unreachable, bad response), `storageFailed` ("signed in but couldn't save the session on this Mac"), `sessionRevoked` (Day 5: "You're signed out. Sign in to keep using rewrite.").
- Window spec (`docs/design/sign-in.md`): one window, two states (email, then code); fields, primary and secondary buttons ("Send a new code", "Use a different email"), disabled and loading states, error placement; Return submits, Esc closes; VoiceOver labels; light and dark; `BrandColor` tokens (emerald text on either background fails contrast: use emerald only as a button fill with white text, 4.5:1); the menu-bar app must activate itself so the field takes keyboard input.
